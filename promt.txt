You are a senior backend/distributed-systems engineer and technical educator.

I want you to build an educational demo that explains and visualizes how a high-concurrency flash-sale system can prevent overselling.

## Problem context

Imagine a flash sale starting at 12 PM:

- Product stock: 500 units
- Potential buyers: up to 2,000,000 concurrent Buy requests
- A naive implementation does:

  1. SELECT stock from PostgreSQL
  2. Check stock > 0
  3. UPDATE stock
  4. Create order

At very high concurrency this can cause severe database contention, poor latency, and—if implemented without proper atomic/transactional safeguards—overselling.

The architecture we want to explore is approximately:

Browser
    ↓
API
    ↓
Redis atomic reservation
    ↓
Allowed / Sold Out
    ↓
Queue
    ↓
Worker
    ↓
PostgreSQL

Redis contains the fast-path inventory reservation.

Conceptually:

stock = DECR flash:product:stock

if stock >= 0:
    ALLOW
else:
    INCR flash:product:stock
    SOLD_OUT

Successful reservations are queued for asynchronous processing.

The user receives something similar to:

"Reserved for 10 minutes. Complete payment before the reservation expires."

A worker consumes the queue and persists orders/reservations to PostgreSQL.

If the reservation expires without payment, inventory should eventually become available again.

The demo must also explain that Redis atomicity alone does NOT magically solve every distributed-system problem.

This is important.

## Mode A — Naive database implementation

Create an intentionally naive endpoint approximately like:

POST /naive/buy

Flow:

request
→ read PostgreSQL stock
→ check stock
→ update stock
→ create order

Make the race condition observable.

You may introduce a configurable artificial delay between SELECT and UPDATE so concurrency problems are easy to reproduce locally.

Track:

- requests
- successes
- failures
- DB queries
- oversold quantity
- latency
- final DB stock

Clearly mark this endpoint as intentionally unsafe and educational.

## Mode B — Redis reservation implementation

Create:

POST /flash-sale/buy

Flow:

request
→ Redis atomic reservation
→ immediate ALLOWED or SOLD_OUT response
→ enqueue successful reservation
→ worker processes reservation/order
→ PostgreSQL persistence

Use a unique request/order/reservation ID.

Make processing idempotent.

Stock must never become negative from successful reservations.

# Phase 5 — Reservation lifecycle

Implement a simple reservation state machine:

AVAILABLE
→ RESERVED
→ PAID

or

RESERVED
→ EXPIRED
→ inventory returned

A reservation should have an expiration time.

For the demo, make TTL configurable, for example:

30 seconds

instead of requiring 10 real minutes.

Provide APIs/actions to:

- reserve
- simulate payment
- expire reservation
- release stock
- inspect reservation state

Make expiration safe against duplicate execution.

Do not allow stock to be incremented twice for the same expired reservation.
